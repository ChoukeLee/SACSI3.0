# SACSI AI 工作台第一阶段需求规格

> 状态：阶段 A/B 已完成本地实现与验证；阶段 C 已接通 L1「完成保洁」人工确认→原子执行→复查闭环（本地验证通过），等待迁移审核和受控上线。法语工作台结果层待办。
>
> 更新时间：2026-09-05
>
> 适用范围：日租、长租、出售及其关联财务
>
> 核心原则：准确性优先。AI 是受控业务入口，不是数据库操作者。

## 1. 产品定位

SACSI AI 与传统页面是两种平级的操作入口。页面点击和自然语言最终必须进入同一套 Business Action，不允许各自维护一套业务逻辑。

```text
传统页面 ─┐
          ├─ Business Action Gateway ─ 权限与业务校验 ─ 原子 RPC ─ Supabase
AI 工作台 ┘
```

第一阶段采用固定流水线：

```text
输入 → 识别意图 → 查询候选记录 → 业务匹配 → 生成操作草稿
     → 人工确认 → 执行受控动作 → 重新查询验证 → 展示结果
```

AI 禁止：

- 直接生成或执行任意 SQL。
- 在客户端或模型上下文中持有 `service_role`。
- 绕过当前登录用户的权限。
- 在用户只要求查询时写入数据。
- 静默补全付款方式、实际付款日期、币种、合同总价等关键事实。
- 用“保存中/已保存”的界面提示代替最终数据库验证。

## 2. 第一阶段范围

### 2.1 输入

第一阶段支持：

- 自然语言文字。
- 图片和财务截图。
- Excel、CSV、PDF。

语音、自动催收、后台自主执行、经营预测不进入第一阶段。

### 2.2 业务优先级

1. 日租：完整查询与高频操作。
2. 长租：完整查询、收款、欠款、续租和退租结算。
3. 出售：完整查询与安全收款；关键合同变更保持严格限制。

## 3. 统一业务对象定位

任何修改动作都必须先解析为唯一业务对象。

房间不得只使用房号定位，最少需要：

```text
项目/楼栋 + 房号 + 业务类型
```

订单或合同存在多个候选时，还需要：

```text
客户或经办人 + 起始日期 + 订单/合同 ID
```

如果无法唯一匹配，AI 只能展示候选项，不能执行修改。

### 3.1 人员身份分离

以下身份必须分开保存和展示：

- 实际客户或租客。
- 经办人。
- 当前系统操作者。
- 销售或中介人员。
- 合同签署人。

兼容期内，若真实客户只存在于备注中，AI 查询可以辅助匹配备注；所有新记录不得继续把经办人写成实际客户。

## 4. 统一确认等级

第一阶段所有写操作都必须确认，区别仅在确认强度。

| 等级 | 类型 | 示例 | 交互要求 |
|---|---|---|---|
| L0 | 只读查询 | 查房态、查欠款、查合同 | 不确认 |
| L1 | 可逆状态操作 | 完成保洁、标记维修 | 展示单步摘要后确认 |
| L2 | 业务和财务写入 | 新建入住、续住、收款、修改缴费截至日 | 展示对象、金额、日期及影响后确认 |
| L3 | 高风险纠错 | 删除、退款、反冲、终止合同、修改总价、批量分账 | 展示修改前后差异；二次确认；限授权角色 |

一次话语包含多个动作时，草稿必须拆成多个项目。执行结果也必须逐项返回，不能只报告“完成”。

## 5. 日租动作目录

### 5.1 第一阶段支持

| Business Action | 用途 | 最低等级 |
|---|---|---|
| `query_daily_booking` | 查询订单、房态、欠款、收款和保洁 | L0 |
| `create_daily_booking` | 新建固定或开放式预订 | L2 |
| `check_in_daily_booking` | 办理入住 | L2 |
| `extend_daily_stay` | 修改离店日期或续住 | L2 |
| `record_daily_payment` | 登记补缴房款 | L2 |
| `check_out_daily_booking` | 实际退房并结算 | L2 |
| `complete_daily_cleaning` | 完成保洁 | L1 |
| `mark_unit_maintenance` | 标记维修及原因 | L1 |
| `cancel_no_show_booking` | 取消未到店、未付款订单 | L3 |
| `transfer_daily_booking` | 转房并同步财务归属 | L3 |
| `reverse_daily_payment` | 撤销错误收款 | L3 |
| `correct_daily_booking` | 撤销错误入住/退房/金额 | L3 |
| `apply_booking_credit` | 将可用余额转至另一订单 | L3 |

### 5.2 日租强制规则

- 新建、续住和转房必须进行日期冲突检查。
- 办理入住前必须确认房间不存在未完成保洁和其他在住订单。
- 实际退房日是结算、房态和统计的业务日期；计划退房日仅作为计划保留。
- 退房必须同步最终金额、未收余额、清洁任务和房态。
- 未付款且未实际入住的订单才允许走简化取消。
- 已付款或已入住订单必须走退款、退房或纠错流程，不能直接删除。
- 开放式入住在收款前必须根据截至日期重新计算真实应收。
- 信用余额转移不得重复计算新现金收入。
- 相对日期必须按 Africa/Abidjan 时区转换，并在确认草稿中显示绝对日期。

## 6. 长租动作目录

### 6.1 第一阶段支持

| Business Action | 用途 | 最低等级 |
|---|---|---|
| `query_lease_position` | 查询合同、租客、月租、缴费周期和未收 | L0 |
| `query_lease_due_detail` | 查询逾期及未来应收明细 | L0 |
| `record_lease_rent` | 登记租金并分配收费期间 | L2 |
| `record_property_fee` | 登记物业费 | L2 |
| `record_combined_lease_payment` | 拆分租金、物业费等组合付款 | L3 |
| `record_lease_deposit` | 登记押金 | L2 |
| `renew_lease` | 续租并建立后续收费周期 | L3 |
| `mark_non_renewal` | 标记到期不续租 | L2 |
| `start_lease_move_out` | 登记实际离房并进入结算 | L2 |
| `settle_lease_deposit` | 押金退款与扣款 | L3 |
| `terminate_lease` | 完成退租并终止合同 | L3 |
| `correct_lease_payment` | 更正金额、日期或覆盖期间 | L3 |

### 6.2 长租强制规则

- 正式合同到期日与租金已缴至日期是两个不同字段，互不覆盖。
- 未收和逾期只使用已确认、由系统管理的 `receivables`；历史待核项目不得进入首页和主业务 KPI。
- 根据 `paid_through_date` 推算的下一期金额只能标注为“预估”，不得混入真实未收和逾期。
- 租金收款必须明确覆盖期间；多房间付款按各房间实际租金分配，禁止平均分摊。
- 房租和物业费合并支付时，优先依据合同固定金额拆分；无法唯一拆分时必须人工确认。
- 实际付款日期未知时，必须分别保存“实际付款日期未知”和“系统补录日期”，不得伪造付款日。
- 退租必须依次处理实际离房、租金结算、其他费用、押金退款或抵扣、合同终止和房态。
- 占位合同、待开业合同或关键字段不完整的合同不得自动生成正式应收。

## 7. 出售动作目录

### 7.1 第一阶段支持

| Business Action | 用途 | 最低等级 |
|---|---|---|
| `query_sale_position` | 查询合同总价、累计已收、未收和过户状态 | L0 |
| `query_sale_payment_detail` | 查询分期计划、到期未收和历史收款 | L0 |
| `create_sale_draft` | 创建信息不完整的销售草稿 | L3 |
| `record_sale_payment` | 登记预付款、分期款或尾款 | L2 |
| `add_sale_installment` | 新增或调整付款节点 | L3 |
| `update_transfer_status` | 更新交房或过户状态 | L2 |
| `correct_sale_payment` | 更正或反冲错误销售收款 | L3 |
| `terminate_sale_contract` | 解除销售合同 | L3，管理员 |

### 7.2 出售强制规则

- 合同总价未知时允许保存草稿和预付款，但不得计算尾款、回款率或完整应收。
- 预付款不得自动视为合同总价。
- 产权状态、当前占用状态和代租管理关系必须独立。
- 已售房仍可能存在有效代租合同；登记租金不得把产权状态改回长租或空房。
- 修改合同总价、退款、解除合同和改变付款计划必须展示全部关联付款及修改前后差异。
- 销售逾期只来源于明确的付款计划节点，不允许按模型猜测。

## 8. 多币种规则

系统结算币种统一为 XOF；页面可显示 FCFA 作为当地名称。所有非 XOF 收款必须保存：

- `original_currency`
- `original_amount`
- `exchange_rate_to_xof`
- `amount_xof`
- 汇率来源或人工确认说明

AI 不得自行选择汇率。用户只提供美元或欧元金额而未提供折算信息时，生成待确认草稿，不直接入账。

## 9. 操作草稿数据结构

```ts
type ProposedBusinessAction = {
  proposalId: string;
  actionType: string;
  riskLevel: "L1" | "L2" | "L3";
  target: {
    projectId?: string;
    buildingId?: string;
    unitId?: string;
    bookingId?: string;
    leaseContractId?: string;
    saleContractId?: string;
    customerId?: string;
  };
  input: Record<string, unknown>;
  beforeSnapshot: Record<string, unknown>;
  expectedEffects: Array<{
    entityType: string;
    entityId?: string;
    operation: "insert" | "update" | "cancel" | "reverse";
    summary: string;
  }>;
  warnings: string[];
  confidence: number;
  requiresClarification: boolean;
  expiresAt: string;
};
```

确认时后端必须重新读取对象版本。如果对象在生成草稿后已变化，旧草稿失效并重新生成，避免多人操作覆盖。

## 10. AI 专用记录

建议新增：

- `ai_jobs`：记录一次文字、图片或文件任务及处理状态。
- `ai_inputs`：记录原始输入、文件私有路径、提取文本和识别结果。
- `ai_proposed_actions`：记录操作草稿、风险等级、确认状态、过期时间和执行结果。
- `ai_action_events`：记录草稿生成、人工修改、确认、拒绝、执行和失败事件。

所有表启用 RLS。文件必须放在私有 Storage bucket。AI 表只保存必要的业务证据，敏感证件不得写入模型提示、普通日志或审计摘要。

## 11. 权限与执行边界

AI 继承当前登录用户权限，不新增“AI 超级管理员”。

| 角色 | 建议允许的 AI 动作 |
|---|---|
| `front_desk` | 日租查询、入住、退房、补款、保洁；不能执行异常纠错和合同财务 |
| `finance` | 财务查询、长租/出售/日租收款；不能创建或终止合同 |
| `rental_sales` | 创建和维护租售合同、日租新建；财务动作按现有授权 |
| `admin` | 全部受控动作，包括 L3 纠错 |
| `boss` | 以查询为主；写权限按最终角色策略配置，不因显示名称获得权限 |

Business Action Gateway 必须执行：

1. 当前会话认证。
2. 角色授权。
3. 对象级业务校验。
4. 幂等键检查。
5. 原子 RPC。
6. 审计记录。
7. 执行后重新查询。

## 12. 审计要求

AI 不是业务 actor。真正 actor 始终是当前登录用户，并记录 `channel = ai`。

每次写操作至少保存：

- 原始输入引用。
- AI 提取结果。
- 操作草稿。
- 修改前快照。
- 人工修改内容。
- 最终输入参数。
- 登录用户与角色。
- `request_id` / 幂等键。
- RPC 返回结果。
- 执行后快照。
- 失败原因或反冲链路。

## 13. 当前系统核对结果与前置缺口

### 13.1 可复用基础

- 日租已具备创建、确认、入住、收款、反冲、退房、折扣、续住、保洁和取消 RPC。
- 长租已有原子财务登记入口和 `request_id` 幂等基础。
- 出售已有原子创建合同和原子收款 RPC。
- 已存在 payments、receivables、ledger_entries、audit_logs 和角色守卫。
- 已有财务统一口径与历史待核隔离机制。

### 13.2 AI 上线前必须修复

1. 长租收款代码当前会把 `expected_end_date` 改成最新 `paid_through_date`；必须停止覆盖正式合同到期日。
2. 日租当前使用 `customer_id` 保存限定经办人；必须增加独立经办人字段，并保留实际客户字段。
3. 长租与出售部分动作通过 `createPrivilegedClient()` 执行；AI Gateway 不得依赖特权客户端绕过 RLS，应改为受控 RPC 内鉴权或当前用户会话执行。
4. 长租收款当前默认付款方式为 `cash`；AI 未收到付款方式时必须要求确认或明确保存为“未提供”，不能静默默认现金。
5. `sale_contracts.total_amount_xof` 当前要求明确金额，无法正确表达“总价待补”；需要增加金额确认状态或允许草稿为空。
6. 多币种信息当前主要依赖备注解析；应升级为结构化字段。
7. 现有 Business Action 分散在页面 Server Actions 中；需要建立统一动作注册表和参数校验层。
8. 缺少 AI 草稿、人工修改和执行事件的持久化记录。

## 14. 第一阶段验收案例

### 14.1 日租误入住删除

输入：`昨天1106并没有入住，帮我删除信息。`

- 将“昨天”转换为阿比让绝对日期。
- 查询并展示所有匹配的 11#1106 订单。
- 唯一匹配且未付款时，展示将取消的订单、应收和房态影响。
- 用户确认后取消订单及应收并恢复房态。
- 不物理删除审计证据。

### 14.2 日租转房

输入：`将11#1106目前的入住信息转移到1103。`

- 校验1103日期无冲突且可入住。
- 展示订单日期、客户、应收、已收和两间房状态变化。
- 原子更新订单、财务归属和房态。

### 14.3 日租统计纠错而非退款

输入：`5#1303住了7晚，不是8晚；没有多收，是原来统计错了。`

- 将应收和已收从错误的8晚金额更正为7晚金额。
- 不创建退款或现金流出。
- 保留修改前后金额和纠错原因。

### 14.4 长租历史付款日期未知

输入：`7#906漏了两次租金，但具体付款日期不知道。`

- 查询月租、已缴至日期和缺失期间。
- 不伪造实际付款日期。
- 展示拟覆盖月份和金额，确认后用补录日记录系统操作。

### 14.5 长租退租押金结算

输入：`11#701已退租，押金扣水电后退了128万。`

- 查询原押金、租金余额和房态。
- 若原押金140万，草稿显示退款128万、扣款12万。
- 未提供扣款明细时标记待补，不能虚构具体水电项目。
- 确认后原子写入退款、抵扣、合同状态和审计。

### 14.6 出售总价未知

输入：`5#504已售，ABOU付了1.1亿预付款，但总价还不知道。`

- 创建销售草稿和预付款草稿。
- 合同总价显示待补；未收与回款率不计算。
- 不把预付款当总价。
- 明确展示产权、占用和过户状态。

### 14.7 已售房继续代租

输入：`登记11#502八月份租金70万。`

- 识别已售产权与有效代租合同同时存在。
- 只更新租赁财务和缴费截至日。
- 不改变产权状态。

## 15. 开发顺序

### 阶段 A：业务边界收口

- 建立 Business Action 注册表和统一返回格式。
- 修复第13.2节的前置缺口。
- 为现有日租、长租和出售 RPC 补齐动作级测试。

### 阶段 B：AI 草稿基础设施

- 建立 AI 任务、输入、草稿和事件表。
- 建立私有文件上传和数据保留策略。
- 实现草稿过期、对象版本校验和幂等执行。

### 阶段 C：文字命令工作台

- 先上线 L0 查询。
- 再上线日租 L1/L2 操作。
- 再上线长租收款与出售收款。
- L3 动作在验收案例全部通过后逐个开放。

### 阶段 D：图片与文件导入

- 先做租金、物业费及两者组合。
- 低置信度、金额冲突和无法匹配项目进入人工复核。
- 押金、退款、维修费、水电费和销售复杂分账后续开放。

## 16. 完成标准

- AI 与传统页面调用同一 Business Action。
- 所有写入均有确认摘要、幂等键和执行后验证。
- 日租、长租、出售分别通过本规格中的验收案例。
- AI 无法使用任意 SQL 或 `service_role` 绕过权限。
- 正式合同到期日、缴费截至日、实际离房日不再混用。
- 实际客户、经办人和系统操作者不再混用。
- 总价未知、多币种和付款日期未知都有明确的数据表达。
- AI 纠错使用取消、反冲或更正链路，不删除审计证据。

## 19. 阶段 C：L0 受控查询工作台

### 19.1 首批查询范围

- 日租：指定日期和楼栋的占用、今日离店、待保洁、预订及可安排入住。
- 财务：按日租、长租、出售或全部业务查询当前未收、逾期及未来 N 天应缴。
- 房源：以“楼栋 + 房号”查询当前房态、生效合同/订单和已确认财务余额。
- 不支持预测利润、自由 SQL、跨权限检索和任何写入动作。

### 19.2 准确性边界

- 模型只允许把自然语言映射到固定查询类型和过滤条件，不负责计算金额，不直接访问数据库，也不生成 SQL。
- 实际取数始终使用当前登录用户的 Supabase 会话，由数据库 RLS 与应用角色权限共同限制。
- 财务金额只统计 `management_status = managed`、未取消且未收余额大于 0 的应收；历史待核与排除项不混入结果。
- 长租和出售只统计生效合同，日租排除已取消订单；逾期统一定义为“到期日早于统计日”，到期当天不算逾期。
- 每次答案必须展示业务范围、统计时点、取数方式和口径说明，不以自然语言掩盖不完整记录。

### 19.3 可选模型分类器

- 固定中文规则无需外部模型即可工作；只有本地规则无法可靠识别时，才把用户本次输入的问题文字发送给模型进行意图分类。
- 当前本地默认使用 DeepSeek：显式配置 `AI_QUERY_CLASSIFIER_ENABLED=true`、`AI_QUERY_PROVIDER=deepseek` 和 `DEEPSEEK_API_KEY`；默认模型为 `deepseek-v4-flash`。
- DeepSeek 请求使用 JSON 输出模式并关闭思考模式；返回结果必须通过查询类型、业务范围及过滤条件的枚举与结构校验，才能进入固定查询服务。
- 如以后切回 OpenAI，只需把 `AI_QUERY_PROVIDER` 改为 `openai`，并配置 `OPENAI_API_KEY` 与 `OPENAI_QUERY_MODEL`；该路径使用 Responses API、严格 JSON Schema、`store: false` 和哈希后的 `safety_identifier`。
- 模型只负责识别意图，不生成 SQL、不计算金额、不访问 Supabase；数据库记录、查询结果、服务角色密钥和数据库密码均不会发送给模型。
- 模型未配置、请求失败或输出不合格时安全降级为“不支持”，不会猜测执行，也不会放宽登录用户的权限边界。

## 21. 文字模型与多模态能力分层

### 21.1 供应商边界

- `deepseek-v4-flash` 继续只负责文字问题的意图分类，不接受图片，也不接触查询结果或数据库记录。
- DeepSeek 当前另有实验视觉模型 `deepseek-v4-flash-vision-exp`；系统把它定义为独立的 `deepseek-vision-exp` OCR 提供方，不因两者使用同一密钥而混用模型职责。
- 现有 Qwen VL、GLM Vision 和 OpenAI Vision 适配器继续保留，后续用同一组匿名化收据样本比较字段准确率，而不是只凭供应商宣传选择。
- 当前 `OCR_PROVIDER` 默认仍为 `mock`，DeepSeek 视觉能力没有在生产环境自动启用。

### 21.2 凭证识别安全规则

- DeepSeek 视觉通道只接受 PNG、JPEG、WebP 和 GIF；PDF 在外发前直接拒绝，后续应先进行本地逐页渲染和文件安全检查。
- 视觉响应必须解析为收据结构化字段；不确定字段保持为空并进入人工确认，不允许直接生成收款。
- 缺少密钥、未知提供方、HTTP 错误和空响应统一返回明确错误，不得把错误消息伪装成 OCR 正文。
- 图片识别只是“提取候选事实”，金额、币种、房号、日期和业务类型仍须与系统记录交叉核对并由人工确认。

### 21.3 本地验证

- 使用不含业务数据的测试图片调用 `deepseek-v4-flash-vision-exp`，API 返回 HTTP 200，确认当前密钥具备该模型访问能力。
- 新增供应商边界测试，覆盖缺少密钥、结构化响应、PDF 拦截和未知提供方安全失败。
- 视觉模型仍标记为实验能力；完成真实凭证基准测试之前不得替换人工录入或确认流程。
