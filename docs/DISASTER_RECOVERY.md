### 本次发现并解决的问题

- 连接池不采纳启动只读参数：源端改用显式只读、可重复读事务，并检查状态；pg_dump 使用该事务的导出快照。
- PostgreSQL 内置 public schema 默认权限：重建会丢失 PUBLIC USAGE；只读核对源 ACL 后在本地恢复该遍历权限，没有新增表数据权限，结构全文校验随后通过。
- 本地邮箱 provider 被关闭：启用邮箱登录、保留全局禁止注册，无需重建账号或改原密码。
- CLI 默认 Storage v1.72.1 不兼容源端对象版本索引，上传报 42P10；仅将演练服务升级到 v1.79.16，固定镜像摘要 `sha256:5fea789899d4dd16bdfdf255b3e60d55f64aabbf6976ba88cb8ed3e2f318f39a`。没有删改生产索引。
- 容器替换后重启本地网关清除旧 IP 缓存，并等待 Auth/Storage 就绪，避免将暂时 502 当作数据丢失。
- 服务启动会改变 Storage 迁移校验和 Auth 会话，因此全库哈希在服务启动前验收，之后另行复核业务表。

本次 PostgreSQL 17.6.1.167、Auth v2.196.0、PostgREST v16.2，完整镜像 ID 见验收报告。没有重放未发布的长租事务迁移。

### 执行前拟定的验收顺序

1. **备份保护**：建立独立、被 Git 忽略且限制访问的备份目录；记录来源、时间、工具版本、完整性哈希和范围。加密密钥必须可在另一台机器取回，不能只依赖本机 DPAPI，否则电脑损坏时备份也可能无法解密。
2. **数据库备份**：按当前 Supabase 官方方法导出角色、结构和数据，明确核对 public/private/Auth/Storage 元数据、函数、触发器、序列和 RLS。导出必须遇错即停；记录一致性边界与恢复点，不将多个不同时间的 REST 分页当作事务快照。数据库连接使用只读事务配置，避免对线上写入。
3. **Storage 和配置**：重新盘点对象，下载存在的对象原始字节，记录哈希并核对清单。当前对象为空也需保存证据；使用合成对象独立验证文件备份/恢复链路，不能伪称恢复了真实图片。单独登记 Auth/SMTP、JWT、API 密钥、部署环境、函数和外部文件的恢复方法。生产密钥不得直接注入演练运行环境。
4. **独立恢复**：新建唯一命名的本地隔离 Supabase 栈与卷，端口仅监听回环地址；不得覆盖既有测试栈。禁止邮件、Webhook、Cron、队列和其他生产外呼。检查备份中的平台版本与扩展兼容性；不自动重放未上线的本地长租迁移。备份 SQL 是可执行代码，先检查外呼和不适用于演练的对象再加载，保留原备份及转换记录。
5. **逐项核验**：对同一备份恢复结果核对表、行数、数据摘要、序列、关系约束、财务关联、权限和审计；使用真实 Auth 服务验证恢复账号重新登录及越权拒绝，不以 Auth 测试桩或手动新建账号代替账号恢复。旧线上令牌不复用。Storage 核对对象字节哈希和权限。测试财务写入只允许在本地恢复副本中进行。
6. **交付证据**：保存不含敏感记录的验收报告、失败项、恢复点、实测备份/恢复用时、恢复命令及演练目录清理方式。本机用时不能直接承诺线上 RTO；本机单副本不等于异地灾备。生产恢复、DNS 切换、密钥轮换和异地备份目的地需另行确认。

只有上述恢复和核验真实执行通过后，才能将“完整灾备演练”标记完成。结构重建测试、JSON 导出成功或 Docker 正常运行都不能替代验收。
