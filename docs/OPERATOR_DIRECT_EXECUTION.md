# Codex 连接器明确指令直办

2026-10-22 开发，随后获准发布。本说明区分代码部署、数据库结构和直办放行，以文末发布记录为准。

## 授权与技术路径

用户明确选择：现有支持业务包含退款登记、收款冲正、历史纠错，在明确指令后直接执行，缺项、歧义或冲突才追问。不增加数据库超级权限，不修改员工角色，不提供任意 SQL/RPC。

服务端原开关 `SACSI_OPERATOR_CONFIRMATIONS_ENABLED=true` 与新开关 `SACSI_OPERATOR_DIRECT_EXECUTION_ENABLED=true` 同时满足才开放直办，默认关闭。身份仍由 Supabase 验证本人 bearer，再核对实时业务权限。`humanConfirmed` 等未知字段被拒绝，预览签名只证明完整性，不证明用户批准。

1. MCP 四个 `execute_*` 写工具保留真实来源、原指令和稳定原请求号。
2. 先查询原号是否已完成；历史完成只报告 `completed_previously / verified:false`，不重写，也不冒充当前指令已核验。
3. 自动生成只读预览，再调用 `/execute`，没有网页确认或模拟代点步骤。
4. 服务端重新核对身份、业务版本、签名中的操作者/请求/账务快照/部署/有效期，再复用原加锁 create/confirm 事务及结果证据核验。
5. 网络错误或回执不完整保留原请求与 unknown 状态；待办恢复只查询，原号未找到也不自动重放或改成网页草稿。

新增端点：`POST /api/operator/v1/{confirmations,collections,bookings,booking-operations}/execute`。仅本人 bearer 可用；原网页端点继续原 cookie、同源和同账号保护。

MCP 平台层审批仍可能出现，不修改用户全局审批设置、不将写工具标成只读。退款只登记已发生退款，不执行银行付款。未实现业务、房态冲突、超额收款、缺应收、汇率不清等仍拒绝或澄清。

## 发布顺序

1. 完成本地完整测试、原生数据库回归、前向升级和旧网页回归。
2. 审核并应用 `20261022202257_operator_direct_payment_audit.sql`：仅扩展单笔日租来源/渠道审计并增加 readiness 函数，保留原锁、授权及核账，不修改业务记录。
3. 发布服务端，直办开关初始保持关闭。
4. 制作 0.6.0 完整候选包并核对哈希、固定路径、本人身份，保留旧包和加密待办。
5. 经明确放行后开启新开关并部署。能力清单须包含 version=1、authorization=explicit_instruction 和所需 workflow。直办启用会要求最低 0.6.0；旧客户端安全拒绝。
6. MCP 配置切换到新完整目录并重启 Codex，确认四个新写工具出现。源码更新不会自动改变运行中的旧工具。
7. 先只读验收身份、版本；真实业务写验收须有明确目标和授权，不用客户现账做冒烟。

没有新迁移时不公布单笔日租直办，接口在第一笔写入前拒绝。其他 workflow 依赖各自原数据库协议版本。旧 `prepare_*` 仍只准备，不偷偷变成写入；原 CLI execute 也保持兼容语义。

## 审计与验收边界

单笔收款沿用本人账号、原请求号、签名预览、锁和证据。新路径执行日志为 `external_codex / explicit_instruction`；旧网页无新元数据仍为 `sacsi_web / authenticated_account_confirmation`。原指令作为请求数据保留，不宣称是不可伪造的用户签名。

自动化测试的身份和数据均为合成且本地隔离，不等于员工真实账号或线上实际业务验收。本轮没有线上客户或账务写入。
