## 分阶段执行与审核

1. **基线与稳定性**：分段计时只记录技术耗时，不记录令牌、客户、金额或原始请求。定位已有 FR 手机视图恢复桌面后立即导航的 React hydration / 迟到流式占位符异常；不靠 suppressHydrationWarning 隐藏，不无证据大改。
2. **请求链路**：在保留真实身份、档案/RLS、退出/撤权边界的前提下消除重复验证；任何不安全的捷径拒绝。应用使用同数据库地域的单区 `dub1`，不迁移业务数据库、不新增多区/付费资源。部署后确认实际区域。
3. **合同读取分层**：列表由数据库筛选分页，独立范围汇总，打开合同才读取完整明细/办理上下文。保留旧全量读取仅用于需要完整证据的导出/特殊流程。所有搜索、状态、项目范围、现金分类、逾期及写后刷新保持。
4. **日历按需读取**：房态窗口、月现金汇总和财务明细分开读取/刷新。首屏只带相关客户，办理时授权搜索候选及合同标记。不能拿窗口订单或当前页付款代替完整财务汇总，不跨用户缓存余额/权限。
5. **集成与统一交付**：普通及原生 PostgreSQL 回归、干净重建、lint/类型/格式/构建、桌面/手机及中文/法语浏览器检查；新迁移先保护快照和兼容性审核，再应用；推送后等待对应 SHA 的 CI 与 Vercel Ready，做只读线上对照和多次计时。

## 发布边界

- 所有生产业务写入为 0：不创建测试客户/合同/订单/收款，不修改真实授权来做试验。
- 不把局部分页明细作为总账，不硬截断旧数据，不凭历史余额推算真实收款。
- 所有新增读取仍以调用者身份受 RLS 约束；失败、未知、被撤权时安全关闭办理。
- 用户未跟踪的 `.local-backups/`、`output/`、`tmp/` 不纳入提交，也不移动/清理。
- 最终按实测报告已达成与未达成预算；CI/Ready 不冒充员工实操验收。若仍有未定位异常，不创建全绿发布标记。

## 读取职责与刷新

- 页面/API继续实时 `getUser`，再查数据库档案和原 RLS；middleware 仅用 SDK 验签预检查/刷新。ES256 使用项目 JWKS，HS256 保留远程回退。退出、撤权、伪造 cookie、过期及签名错误都有隔离 SDK 回归；不信任 JWT 中的业务角色或客户端身份头。
- 数据库角色/项目权限仍按每次查询生效。隔离的退出/撤权测试不等于证明所有已签发 JWT 都即时吊销；直接 Data API 的 access JWT 仍有其有效期边界，不以本轮改造宣称解决令牌全局撤销。
- 合同列表固定每页 25 条，筛选和排序在数据库执行。应收已核销/未收/逾期汇总来自完整项目/楼栋范围，不来自当前页，不改称现金收入。完整合同账务、打印、新建及房间视图在使用时读取。排序固定统一自然顺序，避免本机语言设置影响跨页顺序。
- 长租首屏直接使用当前账号上次选择的项目/楼栋，避免默认楼栋读取后又重复请求。按当前已登录 viewer 隔离的小型导航 cookie 只含两项 ID，服务端用当前 RLS 可见楼栋重新校验，不保存身份令牌、角色、金额或查询结果；显式项目链接优先，无权链接仍拒绝。无偏好仍沿用原默认 11 号楼（无该楼时项目默认范围）；旧本地偏好只在首次无 cookie 时迁移，坏/不可见 cookie 忽略且不再被旧本地范围覆盖。偏好不构成授权，也不新增身份验证请求。
- 新 `daily_calendar_context_rpc` 保留可办理订单的完整收付款证据及关联客户，旧 `daily_calendar_window_rpc` 原定义保留。月净收款独立调用原严格分类器，不用房态窗口订单推算。
- 月度现金卡显示查询截至时间；本机办理成功、页面恢复焦点/可见、主动刷新及新服务端上下文都会重验。失败清旧值，403 清身份相关旧上下文；不把缓存数字称作实时结果。日历日期切换不再重新下载月度全部明细。
- 现金明细沿用每页 50 笔的历史分析 API，完整范围汇总与授权导出保持独立。候选经办人只在打开办理时搜索/分页，保留原名单、黑名单和合同标记；读取失败清旧选择。
- 计时仅包含固定技术标签、耗时和调用次数；不记录身份、金额、客户、问题文本、令牌、cookie 或原始结果。私有响应保持 `private, no-store`，不增加跨用户账务缓存。
