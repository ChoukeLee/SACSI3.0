# SACSI Figma Page Blueprints

## 目标

这份文档把 Figma 重构拆成具体页面蓝图。每个页面都要先画业务主路径，再画异常状态和侧栏状态。

## 通用页面结构

每个主页面都应该包含：

1. App 框架：侧栏、顶部栏。
2. 页面标题区：标题、说明、主动作。
3. 筛选或分段区域。
4. 核心业务内容。
5. 右侧抽屉状态。
6. 空状态、加载状态、错误状态。

## 日租业务页

### 设计目标

让前台能在一个页面内完成：看房态、建入住、确认预订、收款、续住、退房、清洁、维修。

### Desktop 页面结构

1. 页面标题：日租业务。
2. 今日摘要：今日入住、今日离店、未付款、待清洁、维修。
3. 操作工具栏：新建入住、复制今日房态、打印、日期切换。
4. 楼栋信息：固定显示 11#公寓为日租楼栋，不展示无意义楼栋。
5. 状态筛选：只展示当前日租实际存在的状态。
6. 日历主区域：房间行 + 日期列 + 预订条。
7. 右侧订单抽屉。

### 必画状态

- 空房。
- 已预订未付款。
- 已预订已付款。
- 已入住未付款。
- 已入住已付款。
- 非固定离店。
- 已退房待清洁。
- 维修。
- 订单详情抽屉。
- 新建入住抽屉。
- 当前欠款明细抽屉。
- 本月结算明细抽屉。

### 关键体验

- 点击日历空白格直接打开新建入住。
- 点击订单条打开订单详情。
- 订单详情中只出现当前最合理的主操作。
- 更多操作折叠，不占据第一视线。
- 欠款为 0 时不能显示红色待补缴。

## 房源总览页

### 设计目标

让管理者快速理解每栋楼的资产状态，并进入单个房间查看详情。

### Desktop 页面结构

1. 页面标题：房源总览。
2. 资产 KPI：总房源、占用、空闲、维修、待清洁、已售。
3. 楼栋切换：11#、5#、6#、7#。
4. 楼层切换：G、0、1、2、3...
5. 状态结构图。
6. 楼层分组房间卡片。
7. 房间详情抽屉。

### 必画状态

- 11#公寓普通房间卡片。
- 5#公寓大平层/自用办公室。
- 8 楼科建集团办公室整层卡片。
- 已售房间。
- 维修房间。
- 待清洁房间。
- 空闲房间。

### 关键体验

- 不显示数量为 0 且对当前楼栋无意义的状态筛选。
- 特殊资产不强制拆成多个虚假房间卡片。
- 详情抽屉显示业务、备注、审计记录和可用动作。

## 长租合同页

### 设计目标

让租赁管理者从楼栋维度查看合同、租金规模、应缴、待收、逾期，并快速进入收款或合同详情。

### Desktop 页面结构

1. 页面标题：长租合同。
2. 楼栋切换。
3. KPI 卡片：生效合同、月租规模、15天内应缴、待收未逾期、逾期金额。
4. KPI 明细抽屉。
5. 合同状态筛选。
6. 楼层分组合同卡片。
7. 合同详情抽屉。
8. 收款/续租/退租抽屉。

### 必画状态

- 生效合同 KPI 抽屉。
- 15天内应缴 KPI 抽屉。
- 待收未逾期 KPI 抽屉。
- 逾期金额 KPI 抽屉。
- 普通合同卡片。
- 资料待补合同卡片。
- 逾期合同卡片。
- 代管/自有资产说明。

### 关键体验

- KPI 点击不是简单过滤，而是解释数字来源。
- 合同卡片底部按钮居中、间距统一。
- 续费日期、欠款金额不能挤压变形。

## 出售合同页

### 设计目标

把出售业务做成和长租同一套信息架构，但保留出售独有的付款计划、过户状态、合同总额。

### Desktop 页面结构

1. 页面标题：出售合同。
2. 楼栋切换。
3. KPI 卡片：生效出售、合同总额、已回款、待回款、逾期回款、已过户。
4. KPI 明细抽屉。
5. 合同列表或卡片区。
6. 出售详情抽屉。
7. 付款计划抽屉。
8. 过户状态操作区。

### 必画状态

- 已全款。
- 分期中。
- 逾期回款。
- 已过户。
- 未过户。
- 占位出售信息。

### 关键体验

- 与长租 KPI 使用同一交互语言。
- 合同总额、已回款、待回款、逾期回款不能重复表达。
- 付款计划必须在详情中清楚可追溯。

## 财务应收与收款页

### 设计目标

让财务在高密度数据中快速核对金额、来源、客户、房号、备注和审计关系。

### Desktop 页面结构

1. 页面标题：应收与收款。
2. 金额 KPI：应收、已收、未收、逾期、收款率。
3. 收款结构图。
4. Tabs：应收、流水、收据。
5. 筛选栏：状态、来源、楼栋、日期、搜索。
6. 表格。
7. 收款详情抽屉。
8. 欠款明细抽屉。

### 必画状态

- 待收。
- 部分收款。
- 已收。
- 逾期。
- 已取消。
- 来源为日租。
- 来源为长租。
- 来源为出售。
- 手工调整。

### 关键体验

- 表格平铺完整，不裁掉右侧金额。
- 横向滚动只发生在表格内部。
- 备注列可截断，但详情抽屉必须展示完整备注。
- 英文历史备注需要在 UI 层转成中文或被清理。

## 客户档案页

### 设计目标

让用户按业务类型、楼栋、房号和最近活动快速找到客户。

### Desktop 页面结构

1. 页面标题：客户管理。
2. 客户类型 KPI：长租、购房、日租、黑名单、总数。
3. 业务类型筛选。
4. 楼栋筛选。
5. 搜索框。
6. 客户卡片列表。
7. 客户详情抽屉或详情页。

### 必画状态

- 长租客户。
- 购房客户。
- 日租客户。
- 同一客户多业务。
- 黑名单客户。
- 资料待补客户。

### 关键体验

- 客户按楼栋分类时要清楚。
- 长租和出售客户不能误出现在日租客户选择里。
- 搜索框尺寸和其他页面统一。

## 管理驾驶舱

### 设计目标

给老板或管理者一个“今天应该关注什么”的入口，而不是把所有数据堆在首页。

### Desktop 页面结构

1. 总览 KPI。
2. 收款结构图。
3. 房源状态图。
4. 风险清单：逾期、待清洁、维修、资料待补。
5. 楼栋经营对比。
6. 最近操作和审计摘要。

### 必画状态

- 正常经营。
- 欠款较多。
- 待清洁较多。
- 有维修。
- 数据质量异常。

### 关键体验

- KPI 可点击打开对应明细。
- 风险比普通数据更靠前。
- 不把房间卡片海量堆在首页顶部。

## 审计日志页

### 设计目标

让用户知道谁在什么时候做了什么，尤其是财务和订单相关操作。

### Desktop 页面结构

1. 页面标题：审计日志。
2. 筛选栏：时间、操作人、操作类型、对象、房号。
3. 审计表格。
4. 行展开或右侧详情抽屉。

### 必画状态

- 管理员操作。
- AI/业务助手操作。
- 收款操作。
- 订单修改。
- 房源状态修改。
- 缺失操作人修复后的显示。

### 关键体验

- 操作人必须显示为可理解名称，不能只显示短 id。
- 摘要必须中文化。
- 详情里展示原始 metadata。

## Figma 文件建议结构

建议 Figma 文件分 6 个页面：

1. `00 Foundations`
2. `01 Components`
3. `02 App Shell`
4. `03 Daily Rentals`
5. `04 Contracts`
6. `05 Finance + Records`

## 设计顺序

1. 先画 App Shell。
2. 再画组件库。
3. 再画日租业务页。
4. 再画长租合同页。
5. 再画出售合同页。
6. 再画房源总览页。
7. 最后画财务和客户。

原因：日租最复杂，长租和出售最能验证组件复用，房源总览最能验证状态颜色，财务最能验证表格密度。
