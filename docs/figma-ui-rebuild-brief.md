# SACSI Figma UI Rebuild Brief

## 目标

用 Figma 重新定义 SACSI 的视觉系统和核心页面模板，让系统从“不断修补后的业务工具”升级为统一、克制、清晰、好用的房产运营产品。

本次重构允许抛开现有 `DESIGN.md` 的具体视觉规则，但不能破坏现有业务逻辑、权限、数据库结构、财务记录、审计日志和日租/长租/出售的业务状态。

## 设计原则

- 业务优先：页面首先服务前台、财务、管理者的真实操作。
- 统一优先：相同类型的信息必须使用相同组件和交互。
- 数据可信：金额、欠款、已付、逾期、入住状态必须清楚、稳定、可追溯。
- 操作跟手：按钮点击、侧栏打开、筛选切换、状态反馈必须即时响应。
- 长时间使用舒适：避免花哨装饰，降低视觉噪音。
- 中法双语可承载：所有按钮、表格、卡片、侧栏都要能容纳更长的法语文案。

## 不能破坏的业务边界

- 日租房目前只属于 11#公寓。
- 日租订单支持固定离店、非固定离店、已付款、未付款、已离店未付款等业务组合。
- 日租金额、收款、欠款、退房、待清洁、维修状态必须与财务和审计同步。
- 长租合同、出售合同中的占位数据需要可识别，不能与正式资料混淆。
- 财务页面必须实时读取，不能因为缓存造成旧账。
- 所有财务动作必须保留审计日志。
- 房源状态颜色如果重新设计，必须保证每种状态仍然一眼可区分。

## 用户角色

### 前台

核心任务：

- 创建日租入住。
- 确认预订。
- 入住、退房、续住。
- 标记待清洁、已清洁、维修。
- 快速查看今日入住、今日离店、欠款房间。

设计重点：

- 日租日历必须是主视觉。
- 侧栏操作必须比弹窗更常用。
- 付款状态和房间状态不能混在一起。

### 财务

核心任务：

- 查看应收、已收、未收、逾期。
- 补录收款。
- 查账、导出、核对流水。
- 查看审计日志和收款来源。

设计重点：

- 表格要密，但不能拥挤。
- 金额列必须右对齐。
- 收款、欠款、逾期必须有统一颜色和层级。

### 管理者

核心任务：

- 查看各楼栋经营状态。
- 查看日租、长租、出售收入。
- 查看空闲、已售、长租中、维修、待清洁。
- 快速定位异常房间和异常账款。

设计重点：

- 首页和房源总览要有清晰的经营判断。
- KPI 卡片可以点击进入侧栏明细。
- 楼栋切换后所有卡片、图表、列表都要同步变化。

## 核心页面模板

### 日租业务页

页面结构：

1. 顶部业务摘要
2. 今日关键状态
3. 日租操作工具栏
4. 楼栋/日期/状态筛选
5. 日历主工作区
6. 右侧订单操作抽屉
7. 欠款、结算、清洁等明细抽屉

必须解决：

- 点击不跳顶。
- 操作后局部刷新。
- 订单条文字清晰。
- 付款状态不能显示 0 欠款还待补缴。
- 待清洁、维修、已入住、已预订要能一眼分辨。

### 房源总览页

页面结构：

1. 资产总览
2. 楼栋切换
3. 状态结构图
4. 楼层分组房间卡片
5. 房间详情抽屉

必须解决：

- 没有某类状态的楼栋不显示无意义筛选项。
- G 层、0 层、1 层、2 层顺序统一。
- 自用、出售、空闲、维修、长租、日租颜色逻辑统一。
- 类似 8 楼整层办公室这种资产要能作为一个整体卡片展示。

### 长租合同页

页面结构：

1. 楼栋切换
2. KPI 卡片组
3. KPI 明细抽屉
4. 合同卡片/列表
5. 合同详情抽屉
6. 收款/退租/续租操作抽屉

必须解决：

- KPI 卡片点击后展示对应明细。
- 15 天内应缴、待收未逾期、逾期金额不能重复表达。
- 合同卡片按钮居中、间距稳定、不挤压内容。

### 出售合同页

页面结构：

1. 楼栋切换
2. KPI 卡片组
3. KPI 明细抽屉
4. 出售合同卡片/列表
5. 付款计划和过户状态抽屉

必须解决：

- 与长租页面使用同一种 KPI 交互。
- 合同总额、已回款、待回款、逾期回款、已过户各自有独立明细。
- 消除所有中英混杂和乱码。

### 财务页

页面结构：

1. 金额总览
2. 收款结构图
3. 应收/流水/票据 tabs
4. 筛选栏
5. 表格
6. 收款详情抽屉

必须解决：

- 表格列宽稳定。
- 金额右对齐。
- 来源、客户、房号、备注不丢失。
- 备注长文本截断后可在抽屉查看完整内容。

## Figma 交付标准

每个页面至少提供：

- Desktop 1440px 版本
- Tablet 1024px 版本
- Mobile 390px 版本
- 空状态
- 加载状态
- 错误状态
- 至少一个打开的侧栏状态
- 至少一个高风险/欠款/逾期状态

每个核心组件至少提供：

- 默认
- Hover
- Active / Selected
- Disabled
- Loading
- Error 或 Danger

## 代码落地方式

### 第一阶段：Figma 设计定稿

不改业务代码，只确定视觉语言、组件库和 3 到 5 个核心页面。

### 第二阶段：建立代码组件层

把 Figma 组件映射到代码：

- `Button`
- `Input`
- `SegmentedControl`
- `StatTile`
- `BusinessTable`
- `Sheet`
- `RoomCard`
- `StatusBadge`
- `DataVizCard`

### 第三阶段：逐页替换

优先顺序：

1. 日租业务页
2. 长租合同页
3. 出售合同页
4. 房源总览页
5. 财务页
6. 客户档案页

### 第四阶段：删除旧样式

清理散落在 feature 文件里的重复按钮、卡片、表格、抽屉样式。

## 验收标准

- 主要页面看起来像同一个产品。
- 同类按钮、筛选、表格、卡片、抽屉不再出现多种视觉语言。
- 日租、长租、出售、财务的核心操作都能在 1 秒内给出视觉反馈。
- 金额、房号、客户、备注、状态不再因为布局被裁切到无法判断。
- 中文和法语都能正常显示，不出现乱码。
- 每次业务操作仍写入财务记录和审计日志。

## 当前系统现状判断

当前代码已经有共享组件雏形，但视觉统一仍不彻底。长租页面的 KPI 明细抽屉是目前较好的方向，可以作为 Figma 页面交互参考。出售页面已经开始跟进，但仍存在编码乱码和局部样式不统一。日租页面业务最复杂，应作为最终设计系统能否成立的压力测试页面。

新的 Figma 重构不应被旧规则限制，但应继承现有系统中已经验证有效的业务结构和响应模式。
